# H.264 video on pre-Blackwell GPUs

## How it is built (read this first)

The video codecs are **prebuilt binaries** that ship in the package (`libnvdec_h264.dylib`, `libnvenc_h264.dylib`, ...).
There is no source for them in this repository. They were written for Blackwell (RTX 50) and tile frames in the
Blackwell layout; earlier NVDEC/NVENC engines use the classic layout (issue #65 upstream).

- **Decode:** `tools/make_nvdec_t2d.py` changes one byte of the decoder (upstream's tool; the package ships the result as
  `libnvdec_h264_t2d.dylib`).
- **Encode (this fork):** `tools/make_nvenc_t2d.py` patches the Blackwell encoder binary: it redirects the two inline
  tiling loops to replacement loops that write the classic (t2d, block height 2) layout. The plugin
  (`plugin/NVMTLDevice.m`, `nvmtl_nvenc_h264_allowed`) registers the result as a VideoToolbox encoder on Turing only.
  So this is a **binary patch, not a native encoder**: everything past the tiling (engine setup, rate control,
  bitstream) is upstream's closed library, written for Blackwell and untouched here.

The patched library is not committed. Build it from the 2.2.0 package's encoder:

```bash
python3 tools/make_nvenc_t2d.py libnvenc_h264.dylib libnvenc_h264_t2d.dylib   # refuses any other input library
# optional: --low-bar (BAR1), --direct-row / --short-zero (CPU; see Optional speed patches)
codesign -f -s - libnvenc_h264_t2d.dylib
# copy next to NVMTLDriver in /Library/GPUBundles/NVMTLDriver.bundle/Contents/MacOS/, build the plugin, restart apps
```

Set `NVMTL_NO_NVENC=1` in a process to keep it on Apple's encoder.

**Low-latency specification.** ffmpeg's `h264_videotoolbox` (so Sunshine) asks for `EnableLowLatencyRateControl`
whenever it is in low-delay mode. VideoToolbox refuses that on a GPU that is not Apple's (its log says
`VCPRateControlSession: Hardware support is not available`) and the session fails with -12902, so Sunshine falls back to
software x264. Our encoder is constant-QP and does not use that rate-control layer, so in any process where it is
registered the plugin (`plugin/nvmtl_vt_spec_hook.h`) removes that key from H.264 specifications before the call reaches
VideoToolbox (it rebinds `VTCompressionSessionCreate` and `VTCopySupportedPropertyDictionaryForEncoder` in every loaded
image). The same hook fixes a second problem: ffmpeg opens a session and then calls `VTCopySupportedPropertyDictionaryForEncoder`
with it still open; VideoToolbox answers that by instantiating the encoder, the library allows one engine per process
(see Known limits) and the lookup fails with -12908, which ffmpeg treats as fatal. The plugin fetches the (static)
dictionary once before the first hardware H.264 session and serves it from the cache when a later lookup fails that way.
It applies to every app, not only Sunshine. `NVMTL_NO_VT_SPEC_HOOK=1` turns it off. An app that calls VideoToolbox
before it touches Metal still loses its first create, because the plugin (and so the encoder) loads on the first Metal
device.

## Known limits

- **Multi-reference P-frames break Moonlight (fixed by default).** Unpatched, the encoder codes P-frames with up to 3 references (SPS `max_num_ref_frames = 3`). Moonlight rewrites every H.264 SPS to `num_ref_frames = 1` (its "SPS fixup") and decodes with `AV_EF_EXPLODE`, so any P-slice with `num_ref_idx_active > 1` fails. `tools/make_nvenc_t2d.py` patches the library to one reference unless `--keep-multi-ref` is given; see [Single-reference patch](#single-reference-patch).
- **Bitrate is constant quality (QP 23) unless bitrate control is on.** The library ignores `AverageBitRate`, so bitrate varies with content and size. An opt-in controller in the plugin (`NVMTL_VT_RC=1`; see `plugin/nvmtl_vt_spec_hook.h` and `plugin/nvmtl_vt_ratecontrol.h`) steers the QP per frame through `SetProperty(Quality)` toward `AverageBitRate`. With it on, `tools/vt_rc_probe.m` (720p60 synthetic content, hardware encoder) held 8.0 Mbit/s to within 1% and 2.0 / 1.5 Mbit/s to within 15% (key-frame spikes). In Sunshine 2026.914 (Moonlight, H.264, 1080p60, a 25 Mbit/s client setting that Sunshine turns into an 18.99 Mbit/s target) with a full-screen noise window, video on the wire averaged 23.1 Mbit/s with control on (the target plus Sunshine's roughly 20% error-correction overhead, between 19.7 and 25.8 in every second) against 165.6 Mbit/s with it off. Release builds of the plugin remove NVMTL_* variables from a process's environment, so the switch is the line `NVMTL_VT_RC=1` in `/Library/GPUBundles/nvmtl/nvrm610.conf`. *VM-tested on Turing, one setup, short runs.*
- **BAR1 use of the encoder (`--low-bar`, opt-in).** The library maps its working buffers through the BAR1 window and
  zero-fills them: about 33.5 MiB at 1080p, 45.7 MiB at 1440p and 81 MiB at 4K stay mapped for the life of the session. On
  a card with a 256 MB BAR1 and a busy desktop that window can be full, the map fails and the session fails with -12908
  (`nve264: engine bring-up failed`, `cpu map -> 0x51`). `make_nvenc_t2d.py --low-bar` unmaps every window except the
  512 KB doorbell page right after the zero-fill; the GPU keeps its own mapping, so the reference pictures stay in video
  memory and only their CPU alias goes. At teardown the library then removes 9 CPU mappings instead of 16. The peak while a
  session opens is still the 512 KB doorbell plus the 8x-luma pool (about 17 MB at 1080p, 30 MB at 1440p, 67 MB at 4K), so
  an open can still fail when BAR1 is nearly full. If the engine ever needed a window that was removed, the failure would be a
  channel error on the first frame (`nve264: frame N: channel error/timeout`), not a silently wrong picture.
- A second encoder session opened while the first is still open is refused (confirmed on the 2060 Super: -12908) ("engine already in use in this
  process", upstream issue #206). `tools/test_nvenc_h264.py` reports this check (`--overlap-required` makes it fail).
- HEVC encode stays off (a separate bitstream problem upstream).
- The encoder is CPU-bound: CPU time per frame equals wall time per frame, so one core is the limit. With the default
  t2d build under other load that was about 3.6 ms at 1080p; on an idle VM with `--low-bar` it is about 2.3 ms, and
  `--direct-row` plus `--short-zero` cut that further (see [Optional speed patches](#optional-speed-patches)).
  Hypothesis, not measured: much of the remaining cost is the CPU writing the tiled frame through the BAR1 mapping.
- Rows must be a multiple of 16 bytes wide in the replacement loops.
- Only the 2.2.0 encoder is supported; `make_nvenc_t2d.py` refuses other builds.

## Optional speed patches

`--direct-row` and `--short-zero` are opt-in (off unless named) and compose with each other and with `--low-bar`.
They do not include a wait-loop change: the pause-only poll showed no gain on the idle VM, and the corrected sleep
variant brought no CPU saving in a separate experiment.

- **`--direct-row`.** When the row needs no edge pad (`width` a multiple of 16), skip the per-row `memcpy` into the
  staging buffer and let the t2d loops read the source row. Rows that still need padding (for example 1366x768) keep
  the original copy and edge fill. A bad skip would tear the picture or raise a channel error.
- **`--short-zero`.** The per-frame status-buffer `bzero` clears 4096 bytes instead of the full 6.88 MB mapping. The
  CPU only reads the status header after the wait. Too short a clear would channel-error or corrupt the picture, not
  produce a silently good stream.

**Results (VM-tested on Turing).** RTX 2060 Super, macOS 15.8.1, idle VM, median of 3 runs of `tools/bench_nvenc.m`.
Every variant also passed `tools/test_nvenc_h264.py` (four sizes, PSNR ≥ 40, one reference per P slice, low-latency
session, property lookup). All rows are on top of `--low-bar` (and the default t2d / single-reference patches).

## Single-reference patch

Moonlight's SPS fixup and `AV_EF_EXPLODE` need every P-slice to use one L0 reference. The closed encoder (`nve264_encode`
inside `libnvenc_h264`) wrote up to three. `tools/make_nvenc_t2d.py` clamps that to one at the places where it builds
the engine's setup struct and method stream (`0x689a` / `0x689e`, `0x69be`..`0x69c6`, `0x6c7b` / `0x6c7f`) and forces the
"fewer than 3 references" flag, which is what the library already does for the first P-frame after an IDR. The patches
are the same length as the code they replace.

**Results (VM-tested on Turing):** see the test status table above. In the single-reference capture all 119 P slices have
`num_ref_idx_l0_active_minus1 = 0`. PSNR on the synthetic clip drops about 0.2-0.5 dB (about 42.3-42.9 dB), still well above
the 40 dB gate. Long sessions, other resolutions and moving content through Sunshine are not tested.

**Check tool:** `tools/test_nvenc_h264.py` dumps each test stream (`NVENC_PSNR_DUMP=file` in `tools/nvenc_psnr.m`) and
fails if any P-slice uses more than one reference. `tools/h264_refs.py FILE.h264` parses Annex B SPS, PPS and slice
headers (standard-library Python) and exits 1 if any P slice has more than one active L0 reference (`--max-refs N` changes
the limit). It exits 0 only if it found at least one P slice, parsed every NAL unit, and every P slice is within the limit;
B slices are not examined. `tools/test_h264_refs.py` covers Exp-Golomb coding and emulation prevention, and, when the
directory named by `H264_CAPTURES` holds `sr-move.h264` and `reassembled.h264`, two captured streams.

## Running the regression test

On the Mac with the driver installed:

```bash
python3 tools/test_nvenc_h264.py --log ~/nvenc-test.log
```

It builds `tools/nvenc_psnr.m`, encodes at four sizes (1366x768 is not a multiple of 16 wide), decodes with Apple's
software decoder, and requires mean and minimum PSNR of at least 40 dB. Exit 0 passes, 1 fails, 77 means skipped (not
macOS).
